# 复盘：轨迹「有棱有角」与 RGB 段首旧帧

2026-09-11

两个问题都是在「录下来/显示出来的东西不对」这一层被发现的，而且**都被先怀疑
成数据生成侧的故障**（SLAM 出点变慢、相机多投了帧）。实测结论都是：数据本身
没问题，问题出在**消费侧的一处边界处理**。

| | 轨迹有棱有角 | RGB 段首旧帧 |
|---|---|---|
| 症状 | 画到约 20 s 后折线开始切角 | 新 mp4 开头几十帧是录制前的画面 |
| 直观误判 | SLAM 出点频率下降 / 缺帧 | 相机多投了帧 / 编码器预热 |
| 真实根因 | 显示侧降采样上限 400 | 外部队列从不在录制边界清空 |
| 数据本身 | 完好，一直满 30 Hz | 完好，但段首约 1 s **内容错位** |
| 修复位置 | `ui/pose_view_qt.py` | `core/pipeline.py` |
| 回归防护 | `tools/tests/test_pose_view_qt.py` | `tools/tests/test_rgb_prestart_frames.py` |

## 一、轨迹「画了 20 秒后变得有棱有角」

### 1.1 现象

录制过程中，位姿视图里的轨迹线一开始是光滑的，画到大约 20 秒后开始「有棱有
角」，观感像 SLAM 出点频率掉了下来。

这个问题是**紧接在另一个修复之后**被提出来的：前一轮刚修完「帧时间戳回退 →
核心库清 IMU 队列 + 重建地图 → 位姿停发」，用户的原话是

> 你只是把陈旧帧丢了，没有解决我因此缺帧的问题

也就是怀疑棱角 = 之前丢帧的余波。这条怀疑是错的，但它把排查方向钉在了
「到底缺没缺帧」上，反而是破案的关键。

### 1.2 排查：先钉死是哪一侧

第一步不是看绘制代码，而是**验证数据有没有缺**。

把 episode parquet 里的 `slam_trajectory` 列取出来（扁平的
`[t,x,y,z,qx,qy,qz,qw]×n`，不是 3 元组列表），量相邻位姿点的时间间隔：

```
间隔恒为 33.34 ms  →  整段录制一个点都没缺，一直是满 30 Hz
```

数据是满的。**缺帧假设当场排除**，问题只可能在绘制侧。于是转向
`ui/pose_view_qt.py`，很快看到 `_decimated_trajectory`。

### 1.3 根因

`ui/pose_view_qt.py:277` 的 `_decimated_trajectory` 按 **2 的幂**翻倍 stride：

```python
while length > DISPLAY_TRAJECTORY_MAX_POINTS * self._display_stride:
    self._display_stride *= 2
```

这个写法的后果是——**画出的顶点数永远落在 `[cap/2, cap]`，永远不会超过上限**。
上限是 400 时：

| 真实点数 | stride | 画出顶点 | 每段跨度 |
|---|---|---|---|
| 400 | 1 | 400 | 33 ms |
| 401 | 2 | **201** | **67 ms** |
| 801 | 4 | 201 | 133 ms |
| 1601 | 8 | 201 | 267 ms |

30 Hz 下 400 点 = **13.3 s** 就越界，顶点数从 400 腰斩到 201，折线每一段的
跨度直接翻倍——这就是「突然变有棱有角」的那一刻。加上 SLAM 双目 + IMU 初始化
要 ~6 s 才开始出点，`13.3 + 6 ≈ 20 s`，与用户说的「20 秒」吻合。

关键判据是**转角**，不是「走样偏离」：在同一段弧长上，折线的转角随每段时长单调
增大，这才是眼睛看到的「棱角」。真实录制轨迹（334 点 / 11 s / 对角 563 mm，
视图 680×420）实测：

| stride | 每段 | 段中位位移 | **顶点处转角中位** |
|---|---|---|---|
| 1 | 33 ms | 0.66 px | **11.09°** |
| 2 | 67 ms | 1.37 px | **17.37°** |
| 4 | 133 ms | 2.44 px | **22.04°** |
| 8 | 267 ms | 3.95 px | **48.91°** |

（走样偏离也量了，stride 2/4/8 对应最大 1.28 / 4.18 / 11.80 mm——偏离其实不大，
单看这个指标会低估问题，所以判据要取转角。）

### 1.4 评估过的方案

**① 改 `_decimated_trajectory` 用 numpy 切片抽点** —— 否决。
实测比现有的索引列表版**更慢**：`np.asarray(24000 个 tuple)` 要 1.75 ms，
而现有实现只要 0.54 ms。因为轨迹点是 Python tuple 序列，转 ndarray 的开销
超过了切片省下的。**不动这个函数。**

**② 只把上限调大，绘制代码不改** —— 不行。
旧实现是逐点 `_project` + 逐段 `drawLine`，在 6000 点上要 **~13 ms/帧**。
上限之所以一直压在 400，根源就在这个逐点 Python 开销——它是个自我保护。
不批量化就不能提上限。

**③ 最终采用：提上限 + 批量化，两件必须一起做。**

### 1.5 最终方案

1. **上限 400 → 6000**（`ui/pose_view_qt.py:27` 的 `DISPLAY_TRAJECTORY_MAX_POINTS`）
   越界点从 13.3 s 推到 200 s，正常录制再也碰不到。
2. **新增 `_project_many`**（`ui/pose_view_qt.py:331`）——一次批量投影成
   `QPolygonF`，与逐点 `_project` **逐点等价**（有测试断言 < 1e-9 偏差）。
   `_refresh_cached` 改调它。
3. **`_draw_static` 改为一次 `painter.drawPolyline`**（`ui/pose_view_qt.py:377`），
   不再逐段 `drawLine`。

6000 这个值是实测选出来的：它落在「顶点下限 3000 已让折线远密于像素」与
「成本 ≤ 6 ms/帧」的交点上。

### 1.6 代价（实测，有界）

`_refresh_cached` + 整帧 `render` 的耗时：

| 轨迹点数 | 实际画出顶点 | 刷新 | 绘制 | 合计 |
|---|---|---|---|---|
| 6000 | 6001 | 4.20 ms | 1.84 ms | ~6.0 ms |
| 12000 | 6001 | 4.20 ms | 1.82 ms | ~6.0 ms |
| 24000 | 6001 | 4.25 ms | 1.84 ms | ~6.1 ms |

**代价不随会话长度增长**——因为顶点数被上限钳在 6001。配合 25 Hz 刷新 +
30 Hz 重绘，约合单核 14%。主要开销是 `_project_many`（6001 点 3.55 ms）。

### 1.7 回归防护

`tools/tests/test_pose_view_qt.py` 新增两个检查：

- `check_decimation()` —— 对 n ∈ (cap/2, cap, cap+1, 2cap, 4cap) 断言画出顶点数
  ≥ cap/2；并单独钉死 `drawn_vertices(401) >= 400`（旧行为在这里会塌成 201）。
  **已做反向验证**：把上限改回 400 后该断言必然失败。
- `check_projection_equivalence()` —— `_project_many` 与逐点 `_project` 逐点一致。

### 附：同链路上的两个相邻问题（易与本题混淆）

- **轨迹帧率随会话下降**：`update_pose` 在 25 Hz 时间闸门**之前**深拷贝整条轨迹
  `tuple(tuple(p) for p in trajectory)`，让下游 `trajectory is self._rendered_trajectory`
  的判等**恒为假**——而桥接侧 `bridge.py` 的契约正是「新点才重建不可变元组，UI 按
  对象同一性省去无变化重绘」。去掉那次拷贝即可。检测器：
  `widget._rendered_trajectory is traj`（改前必失败）。
- **陈旧帧 → 时间戳回退 → 地图重建 → 位姿停发**：修在**桥接入库处**
  （`online/ORB-SLAM/Examples/fays/TimeRegressionGuard.h`），不能修进核心库——
  库内跳过陈旧帧会让 `GrabImageStereo` 返回未设置的单位位姿而 `mTrackingState`
  仍是 OK，应用侧的 `allFinite()` 判真，会把单位位姿当有效位姿发布，比不修更糟。

## 二、RGB 视频段首混入「录制开始前」的帧

### 2.1 现象

录下的 RGB 视频，开头若干帧是**录制开始之前**的画面。复现样本：
`data/recordings/UMIGripper_Action_AI/videos/chunk-000/gripper_rgb/episode-010.mp4`。
且是「有时候」——并非每段都明显。

### 2.2 排查：四重取证

**① 先排除「多写了帧」** —— mp4 帧数 == parquet 行数。
数量对得上，所以不是写多了，是**内容错位**。

**② 逐帧差分找内容跳变点** —— 每段开头约 **27~28 帧**之后内容突跳，
这个索引与 `Queue(maxsize=30)` 高度吻合。

**③ 跨段帧内容匹配（决定性证据）** —— 新段开头帧与**上一段的末帧**逐帧匹配：

| 新段 | 开头帧最匹配 |
|---|---|
| episode-026 | episode-025 **末帧** |
| episode-025 | episode-024 **末帧** |
| episode-019 | episode-018 **末帧附近** |

跳变之后匹配质量骤降（相似分 ~33 → ~41）。也就是说新视频开头那几十帧，
**物理上就是上一段录制的最后几十帧**。

**④ 段间时间戳间隙** —— 跳变幅度 ≈ 段间 wall_time 间隙 mod 4.295 s
（ep16 1.752/1.737、ep19 3.615/3.580、ep23 3.048/3.023、ep26 4.030/4.031……）。
`hardware_ns` 不是相机硬件时间戳，而是 `time.monotonic_ns()` 截断成 32 位**有
符号**，每 4.295 s 回绕一次——量步长必须用 `(hw[i+1]-hw[i]) mod 2**32`。

**⑤ 日志交叉验证** —— `logs/main.log` 里每段都有
`[录制] 丢帧统计: {'ext:gripper_rgb': N}`（N = 1~13），说明队列在**录制期间
也一直贴着 maxsize**，不只是开头。

### 2.3 根因

`CameraPipeline._start_async` 有一段清空逻辑，注释写着「清空录制前残留的旧帧和
传感器数据」——它排空了 `CameraSlot.frame_queue` 与 `_sensor_queue`，
**唯独漏了 `_external_queues`**；`finish_recording` / `abort_recording` 也都不排空。

而外部队列的**生产侧从设备打开起就一直在投递**（夹爪 RGB 由 bridge 常驻线程
`_rgb_run` 推送），只有录制期间才被 `_write_loop` 消费（每 tick 取 1 帧，不排空）。
于是两类「录制开始前」的帧被原样写成新 mp4 的开头：

1. **上一段停止时没被消费掉的残留** —— 深缓冲 `Queue(maxsize=30)`，1280×960×3
   的帧每张 3.52 MB，满队列 = 30 帧 ≈ **1 s / ~110 MB**。
2. **本段 `_recording=True` 之后、写线程就绪之前累积的** —— `_recording` 是
   **同步**置位的，而写线程要等 `start_episode`（编码器探测 + 建目录，几百 ms）
   跑完才启动，这几百 ms 内外部帧照投不误。

**为什么是「有时候」**：残留量**棘轮式累积**。早期段的跳变索引只有 4/2/5/8 帧，
后期稳定饱和在 27~28——因为生产者速率略高于消费者（见 2.7），队列只涨不跌。

**影响面不止夹爪 RGB**：`ui/main_window.py:970` 的 S80M 双目、`:1170` 的另一个
外部 RGB、`lite_window.py:709/772` 同理，全都是 external source，一并中招。

### 2.4 评估过的方案

**① 在 writer 侧丢弃每段前 N 帧** —— 否决。
`core/egodata_writer.py` 写第 0 帧前没有任何 warmup/丢前 N 帧逻辑，加一个看似
简单，但 N 不固定（随队列残留量在 0~30 之间浮动），N 取大了会误伤正常帧、取小了
治不了本；而且它把「边界语义」藏进了写盘层，真正的问题（队列没清）还在。

**② 在 `_on_gripper_rgb` / bridge 侧做门控**（录制未就绪就不投）—— 否决。
生产侧无从知道写线程何时就绪，要加新的握手状态，把简单问题复杂化。

**③ 只在 `finish_recording` 排空** —— 不够。
`_recording=True` 是同步的，`start_recording` 之后到写线程起来之间仍有几百 ms
的窗口在累积（2.3 的第 2 类）。**必须在 `_start_async` 里、写线程启动之前排空。**

**④ 最终采用：新增 `_drain_external_queues()`，在三处录制边界调用。**

### 2.5 最终方案

```python
# core/pipeline.py:294
def _drain_external_queues(self):
    """排空外部帧源队列（丢弃未消费的旧帧）。"""
    for q in self._external_queues.values():
        while not q.empty():
            try:
                q.get_nowait()
            except queue.Empty:
                break
```

三处调用：

| 位置 | 行 | 作用 |
|---|---|---|
| `_start_async` | `core/pipeline.py:588` | **主修复**，必须在 `_write_thread.start()` 之前 |
| `finish_recording` | `core/pipeline.py:962` | 写线程已停，立即释放 ~110 MB/槽 |
| `abort_recording` | `core/pipeline.py:1000` | 同上 |

对 IMU **无副作用**：被排空帧的 IMU 样本就在它自己的 tuple 里，本就是录制前的
样本，一同丢弃才正确；`_pending_imu` 防丢缓冲也已在更早的步骤清空。

`core/pipeline.py` 是共享模块 → 改完必须 `pack_lite --force` 刷新
`lite_package/`，已执行。

### 2.6 验证

**回归测试** `tools/tests/test_rgb_prestart_frames.py` 走**真实**
`start_recording → _start_async` 路径：

- monkeypatch `core.pipeline.EgoDataWriter` 换成 FakeWriter，
- FakeWriter 的 `start_episode` 由 `threading.Event` 闸门拉住，把启动窗口
  放大到可控；
- 帧的序号编码进像素，逐帧断言。

⚠️ **注意**：`tools/tests/test_imu_pending.py:79` 是直接置 `_recording = True`
来绕过启动路径的，**测不出这个 bug**。新测试必须走真实的异步启动路径，否则
`_start_async` 里的排空根本不会被执行。

结果：

- 正向：12 项断言全过（启动窗口内 70 帧 + 残留 5 帧全部丢弃，之后的真实帧 4/4 落盘）
- **反向验证**：去掉三处调用 → 8 项断言失败，且**视频首帧变成残留帧标记**、
  开头混入 5 帧残留 + 6 帧启动窗口帧——**精确复现用户症状**

**真机验收工具** `tools/check_segment_seam.py`（从任意 cwd 可运行，默认路径按
仓库根解析）。判据是**相对**的——相邻两段常在同一个桌面开录，首帧本来就可能
相似，所以看的是「首帧 vs 上段末帧」是否显著**低于**「首帧 vs 本段自己的倒数
第 30 帧」：

```
修复前的数据（最后 11 段全部命中）：
  episode-048.mp4   首帧vs上段末帧 4.83   vs自己倒数30帧 13.07   ⚠ 疑似残留
  episode-050.mp4                17.61                  61.28   ⚠ 疑似残留
  episode-056.mp4                 9.45                  46.70   ⚠ 疑似残留
FAIL: 11 段疑似以「录制开始前」的帧开头
```

重启主程序后再录一段，同一命令应变成 `PASS: 未发现段首继承上一段末尾的迹象`。

### 2.7 遗留：RGB 相对其他模态的恒定滞后（**尚未处理，待定**）

修 bug 时顺带量出来的第二个问题。用 `hardware_ns` 步长测 8 个 episode：

| episode | 行数 | hw 步长 | 行间隔 | → 生产者帧率 |
|---|---|---|---|---|
| 049 | 273 | 32.64 ms | 33.33 ms | 30.64 fps |
| 052 | 326 | 32.12 ms | 33.33 ms | 31.13 fps |
| 056 | 335 | 32.33 ms | 33.33 ms | 30.93 fps |

**RGB 生产者实际跑 30.5~31.1 fps（均值 30.84），而写线程恒定 30.0 fps**，
净盈余 ~2.8%。这部分**必须丢**（输出就是 30 fps），差别只在丢在哪：

- **现状**（drop-newest，队列满则丢弃本帧）：队列长期贴 maxsize 30
  → 录下的 RGB 画面**恒定落后行时间戳约 1.0 s**（30 帧 ÷ 30 fps），
  相对 tactile / SLAM / parquet 存在固定时间偏移。
- **修复后**：段首从 0 开始，但按 0.84 fps 回涨 → 12 s 的段末约 0.33 s，
  ~36 s 后重新填满。

**建议（未实施）**：把外部队列 `maxsize` 从 30 降到 ~4（`core/pipeline.py:284`）。
滞后降到 ≤0.13 s；**丢帧总数不变**（由盈余决定，不是队列决定的），但由「满了
突发丢一批」变成「均匀铺开」；代价是瞬态卡顿的吸收变浅。

## 三、两条链路的对照

两个问题共享同一个模式：

1. **症状出现在消费侧，但第一直觉总指向生产侧**。轨迹不光滑 → 怀疑 SLAM 出点慢；
   视频开头不对 → 怀疑相机多投。两次实测都证明生产侧是干净的。
2. **破案靠的是「量化不变量」而不是读代码**。轨迹这条是「位姿间隔恒 33.34 ms」；
   视频这条是「mp4 帧数 == parquet 行数」+「跨段末帧匹配」。先证明数据没错，
   才能把搜索范围缩到消费侧。
3. **根因都是一处「漏了对称分支」的边界处理**：`_decimated_trajectory` 的 stride
   翻倍让顶点数永远够不到上限（漏了「到达上限后应保持」）；清空逻辑排空了两条
   队列却漏了第三条。
4. **都必须有反向验证的回归测试**：`check_decimation` 把上限改回 400 必失败；
   新测试去掉三处排空必失败、且复现原始症状。只在正向通过的测试不算数。
